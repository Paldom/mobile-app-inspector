Not reached, and why

  • Article reading view and its toolbar — the crawl stayed on the four top-level tabs to keep the run bounded.
  • Editing, watchlist and contribution flows — gated behind a Wikipedia account; no credentials were entered, by policy.
  • Settings sub-screens, language switching and offline downloads — outside this run's budget.
  • First-run onboarding — already dismissed on this device, so it could not be re-observed without a data clear.
  • Anything a purchase, sign-out or delete control would have opened — never tapped, by policy.

F1Every row of the navigation drawer is unlabelled in the accessibility treemajor medium candidate

All five drawer rows — account, games, places, settings, donate — are actionable containers that expose no accessible name, even though each renders visible text on screen. Two icon-only controls on the Explore feed (the bookmark and share buttons on the featured card) are unlabelled the same way.

Evidence
ux-03-more.json UX-001…UX-005 (ids main_drawer_account_container, _games_hub_, _places_, _settings_, _donate_); ux-01-feed.json UX-001–UX-002 at bounds [743,1064,869,1190] and [880,1064,1006,1190]; screens/03-more.png, screens/01-feed.png.
Steps
cold launch → More → read the accessibility tree; then Home → read the featured card
Expected
Each actionable row announces its own name. Read this as SUSPECTED, not proven: the snapshot folds child text into the nearest clickable ancestor, so the visible labels may be attached to a parent rather than genuinely missing. TalkBack is the only test that settles it.
Standards
MASVS-PLATFORM-1 · M8: Security Misconfiguration
False positive if
the snapshot folded each row's visible text into a clickable ancestor, so the name exists but is attached higher up the tree
Retest
enable TalkBack, swipe through the drawer, and confirm each row is announced by name
Emulator artefact
no — the accessibility tree is the same surface TalkBack reads on a device
F2The binary under review is signed by F-Droid, not by Wikimedianote

The installed APK verifies cleanly (v1+v2+v3) but its certificate is CN=FDroid, O=fdroid.org — this is F-Droid's rebuild, not the artifact Google Play ships.

Evidence
apkscan.json signer.signerDN; pkgdiag.json reports installer '(none — sideloaded or preinstalled)'.
Steps
pull the installed APK → apkscan.py report
Expected
A signature that verifies proves the file was not altered after signing; it says nothing about who the signer is. Compare the certificate against a fingerprint you trust before calling this 'the Wikipedia app'.
Standards
MASVS-CODE-1
False positive if
you intended to review the F-Droid redistribution rather than the Play build
Retest
pull the Play build and compare its certificate SHA-256 against Wikimedia's published fingerprint
Emulator artefact
no

F4Jank rate reads poor, but the sample is far too small to act onminor low candidate

gfxinfo reported 13 janky frames out of 31 (41.9%) across the short tab-to-tab drive, which the thresholds score as 'poor'. The p90 frame time of 2.3 s is dominated by first-draw work, not steady-state scrolling.

Evidence
frames.json — totalFrames 31, jankyFrames 13, verdict poor.
Steps
drive four tabs → profile.py frames
Expected
A 31-frame window on an emulator is a smoke signal, not a measurement. Re-run on physical hardware over a scripted scroll before treating this as a regression.
False positive if
the 31-frame window is dominated by first-draw work rather than steady-state scrolling — which it is
Retest
scripted 30-second scroll on physical hardware, gfxinfo reset first, several hundred frames
Emulator artefact
yes — emulator rendering is not device-grade, and the window is tiny
F5Analytics endpoint dominates the app's network chatternote

During the capture, intake-analytics.wikimedia.org drew 138 DNS lookups — an order of magnitude more than the content hosts en.wikipedia.org (10) and meta.wikimedia.org (4) — and its own TLS SNI confirms the app reached it directly.

Evidence
hosts.json dnsQueries and tlsServerNames; 1,479 packets captured, stats.complete true.
Steps
nettrace.py capture start → drive → capture stop → hosts
Expected
Worth confirming that beacon rate is intentional. The capture is device-wide, so the Google Play hosts in the same list belong to the OS, not to this app.
Standards
MASVS-PRIVACY-1 · M6: Inadequate Privacy Controls
False positive if
the lookups are retries against a single failing resolver rather than distinct beacons
Retest
capture again with an idle baseline subtracted and count TLS sessions, not DNS lookups
Emulator artefact
no
F6System dialogs interrupted the crawl twice and had to be discardednote

A Google Play purchase-verification dialog and, later, an external browser sign-in screen took the foreground mid-crawl. Two captured screens were of those overlays rather than of Wikipedia, and were re-taken; the browser frames were destroyed because they carried a real account address.

Evidence

Steps
bottom nav → More → Saved
Expected
A crawl must check the foreground package every step (uia.py app current) and treat a change as an event, not as app content. Anything captured off-app is evidence about the device, not the app, and may contain personal data.
False positive if
n/a — observed directly, twice
Retest
re-run from a clean AVD snapshot with no Play prompts pending
Emulator artefact
yes — a shared test device accumulates these prompts; a clean snapshot avoids them
